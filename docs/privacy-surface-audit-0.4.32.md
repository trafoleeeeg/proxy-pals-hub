# Аудит поверхностей приватности — Umbra 0.4.32

Дата: 30 сентября 2026. База: merge `abba50b023f020f91b4d7b82333e16cb988ada8d`.
Движок: `umbra-engine-v44.4.5-screen5`, Chromium 152.0.7977.130, Windows x64.
Это начальный реестр покрытия, а не утверждение, что проверены все возможные
способы определения устройства. Не пентест рекламных платформ и не гарантия
нераспознаваемости. После исходного аудита добавлено минимальное исправление
редактора и серверной записи MEM-01 (см. ниже); движок не пересобирался.

## Метод и границы

- Одноразовые синтетические сессии, локальные HTTP origins 127.0.0.1/localhost.
- Реальные OOPIF (проверяется другой processId), dedicated workers; отдельные
  штатные hardware/screen fixtures также проверяют заявленные ими контексты.
- Обычный режим, строгий с разрешёнными аппаратными API на точном origin,
  обычный режим с изоляцией шрифтов.
- Сетевые запросы диагностического rendering fixture разрешены только к его
  loopback-серверу. Это ограничение теста, не доказательство сетевой защиты приложения.
- Реальные cookies, аккаунты, прокси и производственная БД не используются.
  Имена GPU и аппаратные данные не выводятся в отчёт.
- Нативный движок взят из распакованного опубликованного архива, а не из
  заново собранного бинарника. Повторная компиляция не проводилась.
- Это один физический Windows-ПК. Равенство между contexts не доказывает
  независимость от железа. Для неё нужен повтор одного профиля на других ПК.

Различаем: **раскрытие** (наблюдаемые свойства хоста), **несогласованность**
(противоречащие друг другу или версии движка значения), **нормальный общий сигнал**
(совпадение допустимо), **не проверено** (нет доказательства ни защиты, ни утечки).
Сайт обычно получает признаки класса устройства, а не его однозначный серийный
номер. Нельзя считать любое совпадение хеша доказательством связи аккаунтов.

Разница между строгим режимом с исключением и строгим без исключений важна:
здесь аппаратные API намеренно разрешены. Нельзя представлять этот результат
как обход строгих запретов. Изоляция шрифтов отдельно сохраняется при разрешении
других API. Полноту набора и DOM/CSS/worker lookup покрывает отдельный
`test-fonts-native.cjs`, а не этот короткий rendering fixture.

## Новый дефект согласованности: диапазон памяти (MEM-01)

Полный desktop-прогон на этом же движке после расширения теста: **139/139**,
без ошибок и пропусков, с обязательными нативными проверками. Он включает
локальные HTTP/SOCKS auth/failure fixtures и lifecycle workers. Это не заменяет
внешний DNS/ICE/IPv6 challenge или сетевой захват на реальном подключении.

В закреплённом исходнике Chromium
`third_party/blink/common/device_memory/approximated_device_memory.cc`
настольная ветка ограничивает результат диапазоном **2–32 ГБ**; Android отличается.

Наши `normalizeFingerprint`, редактор, frontend validation и оба нативных
patch-файла всё ещё используют прежний набор **0.25, 0.5, 1, 2, 4, 8**.
Нативный тест проверяет совпадение с нашей политикой, поэтому зелёный результат
не обнаруживает несоответствие политике актуального Chromium.

- 0.25 / 0.5 / 1 для текущего настольного движка — подтверждённая по коду
  несовместимость с его обычным диапазоном, а не утечка настоящей памяти.
- 2 / 4 / 8 допустимы. Значение 8 не означает, что профиль ошибочен.
- Недоступность 16 / 32 сужает модель; нельзя просто разрешить их в UI:
  текущий native API их отвергнет.
- Стандартные Windows-presets сейчас используют 4 / 8 и этим дефектом
  диапазона непосредственно не затронуты.
- Исправлять согласованно frontend, server validation, client normalization,
  native API, Blink, HTTP hints, workers и тесты. Учесть клиентов старой версии.
  Сохранённые профили не перегенерировать и не мигрировать молча.

Источник поведения — исходники закреплённого Chromium, не таблица конкурента.
Общие пояснения: [Device Memory API](https://www.w3.org/TR/device-memory/),
[MDN deviceMemory](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/deviceMemory).
Границы являются особенностью реализации и могут меняться с версиями.

## Реестр остальных поверхностей

### MEM-01: совместимое ограничение записи (после аудита)

Редактор, одиночное создание/сохранение, массовое создание/изменение памяти
и копирование допускают только 2/4/8 — пересечение допустимого диапазона
Chromium с возможностями screen5. 16/32 не предлагаются до обновления native API.
Старое значение показано в редакторе с предупреждением: для сохранения полной
формы или копирования такого профиля нужно явно выбрать поддерживаемую память.
Массовое изменение заметок/папки или другого параметра без памяти остаётся доступно.
Чтение и запуск старых профилей не менялись, база не мигрируется.
Поэтому уже сохранённые низкие значения продолжают действовать до явного выбора
пользователя: это предотвращение новых несовместимых настроек, а не полное
исправление старых отпечатков или поддержка диапазона 2–32 в движке.

| ID / поверхность | Статус сейчас | Следующее доказательство / действие |
| --- | --- | --- |
| ID-01 UA, UA-CH, platform, appVersion, язык, Intl, часовой пояс | Есть прежние тесты и нормализация, не новый полный аудит | Сравнить JS + реальные HTTPS Accept-CH/Critical-CH + iframe/worker; проверить правила brands и architecture |
| SCR-01 screen, DPR, CSS color/orientation | Частично проверено нативно | Zoom, resize, fullscreen, внешний монитор, mixed DPI, screen details, события смены монитора |

| GPU-01 WebGL/WebGPU | Разрешённые API нативные, аппаратный backend доступен | Сравнить limits/features/extensions/precision/shaders/adapter info на нескольких ПК; не выдавать другое название карты без реализации |

Новые API и обновления Chromium требуют регулярного пересмотра.

## Порядок исправлений и критерии приёмки

1. **MEM-01 и ID-01:** устранить подтверждённые несогласованности в рамках
   документированной семантики версии движка. Не включать новые случайные seeds.
2. **NET-01…04:** проверить маршруты до заявления «реальный IP не утекает».
   Для внешнего DNS/ICE доказательства потребуется контролируемая инфраструктура;
   адреса и сырые сетевые трассы не отправлять сторонним тестерам без согласования.
3. **GPU/CAN/AUD:** сначала сравнительные измерения на разных ПК, затем
   проектирование изоляции. Одна замена renderer string или getImageData не решение.
   Программный backend — отдельный исследовательский режим, не незаметный GPU.
4. **OS/CSS/PERF/CTX:** расширять матрицу контекстов и платформ, не объявлять
   непротестированные поверхности закрытыми.

Для каждого исправления: воспроизводимый провал до изменения → целевой тест
после → совместимость обычной страницы → второй профиль → рестарт → регрессии.
Для аппаратной независимости дополнительно повторить на другом железе.
Сравнивать с обычным браузером на том же Chromium; набор строк и API — не всё
поведение браузера. Гарантию обхода антифрода из этих тестов делать нельзя.

Сохранность данных, sandbox и контроль разрешений обязательны. Нельзя возвращать
доступ к устройствам, отключать безопасность или скрывать диагностические ошибки
ради более «обычного» вида. Если прозрачного безопасного решения пока нет,
ограничение остаётся явно указанным.

## Дополнительная сетевая проверка: 30 сентября 2026

Расширен `desktop/test/runtime-electron-harness.cjs`, режим `network`.
Использован опубликованный screen5, временные сессии и только loopback-серверы;
рабочие профили, cookies, внешние прокси и сторонние тестовые сайты не затрагивались.

- HTTP/HTTPS и настоящие Chromium WS/WSS работают через аутентифицированный
  HTTP-прокси до сбоя. Для обоих WebSocket-подключений проверены авторизация
  на upstream и получение handshake целевым сервером.
- Принудительное завершение локального proxy worker закрывает открытые WS/WSS.
  Новые запросы всех четырёх транспортов не достигают целевых серверов.
- Отключение upstream при живом bridge также закрывает WS/WSS и не приводит
  к прямому соединению. HTTP может вернуть 5xx от bridge — это отказ прокси,
  а не доставка запроса целевому серверу.
- После сбоя отдельная контрольная direct-сессия достигает HTTP/HTTPS-серверов:
  отрицательный результат не объясняется отключением самих тестовых серверов.

Подтверждённой ошибки в этой части runtime не обнаружено; добавлена регрессионная
проверка, рабочая логика прокси не изменялась. Это не доказательство отсутствия
DNS/IPv6/ICE-утечек или идентичного поведения при смене сети. QUIC в harness
отключён; WebTransport не измерялся. Сценарии сбоя WS/WSS проверены с HTTP-upstream;
существующие отдельные проверки SOCKS5/HTTPS-прокси покрывают авторизацию HTTPS,
но не заменяют аналогичную матрицу WebSocket-сбоев для каждого протокола.

## Воспроизведение

Из корня репозитория, передавая абсолютный путь к распакованному screen5:

```powershell
node desktop/engine/run-rendering-audit.cjs <absolute-electron.exe>
node desktop/engine/run-screen-native.cjs <absolute-electron.exe> hardware
node desktop/engine/run-screen-native.cjs <absolute-electron.exe> screen
$env:ELECTRON_OVERRIDE_DIST_PATH = '<absolute-directory-containing-electron.exe>'
$env:UMBRA_REQUIRE_NATIVE = '1'
node --test --test-name-pattern 'HTTP/SOCKS5' desktop/test/runtime-native-smoke.test.cjs
```

Первый runner теперь включает третий режим `font-isolated` и проверяет отсутствие
доступа к host Arial через CSS в main/OOPIF. Сырые GPU-имена/пиксели не выводятся.
Результаты не являются прогоном реальных рекламных кабинетов или BrowserLeaks.
