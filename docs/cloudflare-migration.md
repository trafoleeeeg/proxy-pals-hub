# Перенос Umbra с Lovable

Цель: разработка из локального Git-репозитория, серверная панель в Cloudflare
Pages Functions, база и Auth в собственном Supabase. Адрес —
`https://umbra.mafiatrafa.com`. Windows-релизы и закреплённый движок остаются
в текущем GitHub-репозитории.

Этот документ и новая команда сборки готовят инфраструктуру. Они сами не
переносят данные, не меняют рабочую БД и не переключают установленные клиенты.
Публичные npm-пакеты сборочного помощника Lovable пока сохранены: их выполнение
локально/в Cloudflare не запускает агента Lovable и не требует его кредитов.

## Cloudflare Pages

Подключённый репозиторий: `trafoleeeeg/proxy-pals-hub`.

| Поле | Значение |
| --- | --- |
| Framework preset | None |
| Root directory | Корень репозитория |
| Build command | `node scripts/build-cloudflare.cjs` |
| Build output directory | `dist` |
| NODE_VERSION | `24` |
| BUN_VERSION | `1.4.2` |

Проверочную публикацию создавать из ветки с командой `build:cloudflare`, а не
из старого `main`. После проверки и слияния переключить production branch на
`main`. Домен подключать после проверки нового backend.

Установка зависимостей использует `bun.lock`. Команда через `node` выбрана
специально: она не загружает старый `.env` автоматически. Для ручного запуска
через Bun использовать `bun run --no-env-file build:cloudflare`. Все значения
передавать в окружении процесса. Обычный `build` и Lovable-сборка сохраняются.

Сборка создаёт Pages worker, проверяет анонимную локальную панель, соответствие
RPC и ресурсов, добавляет два поздно созданных файла в `_routes.json`, проверяет
отсутствие заданных серверных секретов в публичной панели. Затем запускается
`scripts/verify-cloudflare.cjs`: SSR формы входа, анонимная оболочка `/app`, отказ
RPC без авторизации и целостность статических файлов. Эта проверка блокирует
исходящие запросы и не требует рабочей базы. TanStack может сериализовать
Unauthorized в HTTP 200: проверяется декодированный отказ без результата,
а не только статус HTTP.

Pages перенаправляет HTML-файлы на clean URL, а desktop updater намеренно
использует `redirect: "error"`. Поэтому только Cloudflare output получает
точечное внутреннее правило `/_umbra-panel.html /_umbra-panel 200`; оба пути
исключены из Functions. Bytes и SHA-256 manifest не меняются. На живом preview
проверять исходный `.html` без разрешения redirects, размер и hash всех ресурсов.

Эта офлайн-проверка использует собранный worker в Node. Работа в настоящем
Cloudflare runtime и вход в перенесённую базу дополнительно проверяются на
проверочной публикации.

## Переменные и секреты

| Имя | Назначение |
| --- | --- |
| `VITE_SUPABASE_URL` | URL собственного Supabase, встраивается в браузер |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Publishable либо legacy anon key, встраивается в браузер |
| `SUPABASE_URL` | Тот же URL на сервере |
| `SUPABASE_PUBLISHABLE_KEY` | Тот же публичный ключ на сервере |
| `SUPABASE_SERVICE_ROLE_KEY` | Серверное создание и управление сотрудниками |
| `APP_ENCRYPTION_KEY` | **Исходный ключ** шифрования cookies и секретов прокси |

Два `VITE_*` задать в build environment. В текущем Wrangler-managed Pages
проекте plaintext-переменные UI не попадали в сборку; сохранение тех же значений
как encrypted secrets устранило проблему. Это касается также `NODE_VERSION` и
`BUN_VERSION`. Публичный Vite-ключ всё равно намеренно попадает в браузерную
сборку, encrypted storage не превращает его в серверный секрет.
Четыре серверные переменные хранить
как encrypted secrets для Functions. Это также сохраняет runtime bindings при
публикации конфигурации Wrangler, в которой нет `vars`. Сборка и её офлайн-тест
не требуют действительных серверных секретов. Значения ключей не помещать в Git, PR, логи
или переписку. `VITE_*` по назначению публичны после сборки; туда не подходит
service-role/secret key. Новый Supabase service key не заменяет исходный
`APP_ENCRYPTION_KEY`.

На новой площадке должны совпасть build-time и runtime URL/публичный ключ.
Production и preview настраиваются отдельно. Preview не подключать к рабочей
базе до завершения проверки переноса.

## Данные и доступ

### Исходный ключ шифрования

Lovable хранит сохранённые Secrets как write-only: экспорт базы не переносит
`APP_ENCRYPTION_KEY`, а новый ключ не расшифрует существующие записи. Для этого
случая подготовлены временные server functions и [локальное DPAPI-хранилище](key-transfer-vault.md).
Операция в `key-transfer-config.server.ts` **по умолчанию выключена**.

Перед активацией создать локальный запрос получателя (TTL 30 минут), закрепить
только его публичный manifest в серверной конфигурации, проверить CI и получить
подтверждение владельца непосредственно перед включением/публикацией. Экспорт
разрешён только POST на старом origin, после свежего password AMR, проверки Auth
и `is_superadmin`; обычного владения командой недостаточно. Браузер получает
только RSA-OAEP/AES-GCM контейнер для закреплённого получателя. Значение ключа,
cookies, ciphertext в базе и подтверждения сохранения не изменяются.

После приёма контейнера проверить синтетическую canary и сразу выключить
экспорт/удалить временную операцию. Сервер не хранит одноразовый флаг между
репликами: ограничение обеспечивается фиксированным получателем и сроком,
а не обещанием единственного HTTP-запроса. Локальный успешный приём **не**
доказывает правильность секрета в Cloudflare: до переключения нужна отдельная
фиксированная canary-проверка target runtime и проверка восстановленной БД.

### Экспорт и восстановление

1. Дождаться готовности целевого Supabase и определить, есть ли в нём прежние
   данные. Сообщение «Restoration in progress» само по себе не подтверждает
   перенос из Lovable.
2. В исходном Lovable: Cloud → Overview → Advanced settings → Export project
   data. Скачать полный экспорт в защищённое локальное хранилище. Отдельно
   сохранить файлы Storage и исходный ключ шифрования: они не входят в дамп БД.
3. Подготовить план восстановления после просмотра структуры архива. Полный
   PostgreSQL backup не вставляется в SQL Editor и не накатывается вслепую на
   служебные схемы Supabase. Не применять `--clean` как способ обойти конфликты.
4. Проверить перенос `public`, нужных данных `auth` и `private`, включая
   `private.super_admins`, `private.profile_close_receipts` и
   `private.profile_cookie_save_proofs`. Сохранить UUID пользователей и связей.
5. Сверить migration ledger, схемы, RLS, grants, RPC, триггеры и точные количества
   записей. В текущей версии 59 миграций, последняя —
   `20261010100000_cookie_save_lineage.sql`. Сверять число с фактическим тегом
   перед переносом. Не выводить содержимое cookies и пользовательские строки.
6. Проверить два задания pg_cron: `umbra-audit-retention` и
   `umbra-profile-trash-retention`. Тестовый restore не должен неожиданно
   запускать задачи удаления данных до проверки результата.
7. В Supabase Auth отключить **Allow new users to sign up**; оставить вход
   email/password и административное создание сотрудников. Проверить запрет
   прямого `/signup`, а не только отсутствие кнопки на странице. Настроить Site
   URL и разрешённые redirects. Войти владельцем и проверить его права.
8. Проверить доступ разных ролей, расшифровку, запуск/закрытие тестового профиля,
   подтверждение cookies, повторный вход, отсутствие доступа без авторизации.

## Переключение

Для финального экспорта согласовать окно переноса: закрыть рабочие профили,
дождаться подтверждения очереди сохранений и остановить изменения на старой
площадке. Это исключает расхождение двух баз во время копирования.

Текущий установленный клиент закреплён за старым origin. Для нового домена
нужен отдельный проверенный Windows-релиз с обновлённым `DEFAULT_APP_URL` и
проверками IPC. До этого старую площадку сохранять доступной клиентам.

Клиент перехода закрепляет `https://umbra.mafiatrafa.com` одновременно в main
и sandbox preload; старый Lovable origin больше не получает privileged IPC.
Редирект со старого домена не заменяет этот релиз: main блокирует переходы
между origin. `UMBRA_APP_URL` по-прежнему работает только в unpackaged dev-клиенте.
Полная пересборка Chromium для смены хостинга не нужна: используется прежний
закреплённый и проверенный движок, а Windows installer собирается в GitHub Actions.

Перед запуском desktop CI настроить **публичные repository variables** GitHub:
`UMBRA_SUPABASE_URL` и `UMBRA_SUPABASE_PUBLISHABLE_KEY`. Они передаются в два
`VITE_*` build-поля через `node scripts/build-cloudflare.cjs`. Пустые значения
блокируют сборку, подстановка старого `.env` не допускается. Это только URL и
publishable/anon key целевого проекта: service-role и `APP_ENCRYPTION_KEY` сюда
не помещать. Сверить target build/runtime и соответствие панельных RPC до релиза.

Публичный кэш панели разделён по SHA-256 exact origin, а sealed pointer содержит
schema и origin. Старый плоский `panel-bundles/active.enc` и чужие pointers не
подхватываются и не удаляются, в том числе при большей старой revision. Это
изолирует код панели, **не** profile partitions. Не менять appId/name/productName,
`persist:umbra-app`, `persist:profile-${UUID}`, userData и namespaces cookies,
резервов восстановления, вкладок, закладок, consent и session-outbox. Не чистить
их ради нового входа или разрешения конфликтов.

На новом origin и новом Supabase нужен свежий вход в панель; JWT и localStorage
со старого домена не копируются. Это не выход из сайтов внутри профилей: их
сессии используют отдельные сохраняемые partitions. До переключения закрыть
профили и дождаться подтверждённого пустого outbox. При восстановлении сохранить
UUID, `cookies_updated_at`, receipts и cookie-save proofs; неподтверждённый outbox
или конфликт не обнулять. Проверить тестовый запуск, закрытие, повторный запуск
и подтверждение сохранения без чтения содержимого рабочих cookies в логи.

В Cloudflare Pages добавить custom domain `umbra.mafiatrafa.com`, затем у Njalla
добавить CNAME `umbra` на адрес **реально созданного** проекта `*.pages.dev`.
После выпуска TLS проверить серверные функции на новом домене. Основные NS,
записи сайта и почты для этого менять не требуется.

Lovable отключать после успешной проверки клиентов и отсутствия обращений к
старым сервисам. До переключения rollback возвращает старую площадку. После
появления записей в новой базе возврат требует сверки и переноса этих изменений;
одна смена DNS может вернуть устаревшие сессии.
Клиентский rollback выпускать отдельной более новой версией с прежним единственным
origin и проверенными его ресурсами; не добавлять второй trusted origin и не
включать packaged environment override. Возврат к старой базе после новых записей
требует отдельной согласованной сверки данных, а не только смены адреса клиента.
