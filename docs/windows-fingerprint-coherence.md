# Согласование отпечатка Windows с прокси: первый этап

## Закрытие и аварийное восстановление

Крестик сразу скрывает оболочку и блокирует сеть профиля. Запись профиля и
блокировка повторного запуска остаются до завершения сохранения. Остановка
workers и закрытие соединений запускаются параллельно; команды отключения
отладки не ждут ответа команды остановки, который сам может зависеть от
отключения отладчика. Для SharedWorker требуется событие уничтожения target,
для ServiceWorker — завершение stopAllWorkers. При реальном отказе или
отсутствии завершения за 15 секунд контекст остаётся заблокированным до
перезапуска. Это не обещание закрытия за 15 секунд при зависании диска: запись
cookies и долговременная передача в outbox должны закончиться успешно.
Ошибка сохранения возвращает окно для повторной попытки.

Зашифрованный cookie checkpoint хранит признак незавершённой сессии и исходную
облачную revision. После сбоя локальные данные восстанавливаются, если облако
по-прежнему содержит именно эту исходную revision. При конфликте с независимым
облачным изменением запуск отклоняется, обе версии сохраняются. Признак recovery
снимается лишь после успешного закрытия, сохранения и передачи в outbox.
Старые снимки без этих метаданных сохраняют прежние правила; восстановить
изменения, которые прежняя версия не записала на диск, невозможно.

Cookie changes объединяются в окно 300 мс без бесконечного откладывания при
частых изменениях. Запись шифруется, временный файл проходит sync перед rename;
периодический checkpoint остаётся каждые 30 секунд. Это не нулевой RPO: ещё
не записанные изменения могут потеряться, особенно при отказе накопителя.

Нативный тест принудительно завершает только отдельный тестовый browser process
после sync следующего временного снимка, но до его rename. После перезапуска
проверяются предыдущие session cookies, localStorage/CacheStorage, защита с
первой строки workers и согласованность HTTP/JS. На Windows используется DPAPI.
Это проверка аварии процесса, **не имитация физического отключения питания**,
не гарантия сохранения любых IndexedDB-транзакций/несохранённых форм и не
доказательство отсутствия всех аппаратных утечек. При отключённом ПК код
штатного закрытия исполниться не может; защита обеспечивается до аварии и
заново устанавливается перед использованием профиля после запуска.

## Наборы Windows и нормализация — выпуск 0.4.31

Ранние разделы ниже описывают ход разработки до нативной сборки экрана.
Решение не выпускать её действовало до устранения OOPIF CSS-расхождения;
в 0.4.31 этот конкретный тест проходит. Остальные явно перечисленные границы
защиты и совместимости сохраняются.

Новые Windows-профили выбирают связанный набор ОС, экрана, логических потоков
и сообщаемой памяти. Редактор позволяет явно применить другой набор; язык,
пояс, настройки защиты, стартовый адрес и cookies от этого не меняются.
Индивидуальные значения остаются доступными. Существующие профили автоматически
не перегенерируются. GPU и наборы шрифтов для новых Windows-профилей не получают
случайных названий оборудования, которое движок не эмулирует.

Windows UA формируется клиентом канонически, а не берётся произвольно из поля.
Согласно [Chromium UA reduction](https://www.chromium.org/updates/ua-reduction/),
в UA используется `Chrome/<major>.0.0.0`, а фактическая полная версия установленного
движка передаётся через Client Hints. `navigator.appVersion` согласован с UA,
включая workers. Явный выбор Windows 10 имеет приоритет над устаревшим NT 11
в сохранённой строке UA. Основной язык ставится первым; теги канонизируются,
дубликаты убираются. Поддерживаются все используемые здесь memory buckets
от 0.25 до 8; это не показание физического объёма RAM.

Нативный тест сравнивает UA/appVersion/UA-CH, параметры страницы и workers,
а также CSS device-width/device-height/resolution с JavaScript screen/DPR.
Основной документ проходит; в OOPIF обнаружено расхождение: CSS может получать
реальные размеры/DPI. Это **незакрытый канал**, явно отражённый в редакторе и
диагностике `UMBRA_SCREEN_IDENTITY_AUDIT`, не успешная проверка защиты OOPIF.
CDP не принимает setDeviceMetricsOverride для iframe targets. Подмена matchMedia
в JavaScript не решает проблему настоящих CSS-правил и не используется. Sandbox
и site isolation ради обхода ограничения не отключаются. Строгий режим тоже
не закрывает этот CSS-канал. Владелец выбрал не выпускать обновление до устранения
проблемы. Отдельный `runtime-screen-coherence.test.cjs` блокирует выпуск, пока
настоящая stylesheet внутри OOPIF не начнёт видеть экран профиля. Версия клиента
не поднята; эти изменения не следует объединять в main с красным тестом.

Это ограниченный набор проверок, не доказательство неотличимости от Chrome
и не эмуляция GPU/Canvas/audio/шрифтов или всей геометрии окон и многомониторной
конфигурации. Согласование может изменить значения,
которые старый клиент сообщал сайту; cookies и облачная запись профиля при запуске
не переписываются.

После успешной проверки выходного IP настольный клиент делает необязательный
HTTPS-запрос к `ipapi.co` **через ту же временную прокси-сессию**. Сервис видит
выходной IP прокси, но не получает cookies профиля или учётные данные прокси.
Ответ принимается только при совпадении IP с результатом проверки соединения.
Если геосервис недоступен или вернул неподтверждённый ответ, проверка прокси
остаётся успешной, а часовой пояс считается неизвестным.

Подтверждённый пояс сохраняется вместе с последним проверенным IP. При смене IP
старый пояс очищается. Для нового профиля выбор уже проверенного прокси задаёт
этот пояс автоматически. У существующего профиля несовпадение показывается в
редакторе с кнопкой явного применения: без действия владельца его отпечаток
не меняется. Геолокация IP может ошибаться, а смена пояса действующего профиля
может повлиять на сессию сайта.

Это не эмуляция GPU, Canvas, аудио или сетевого TCP-стека. Обычный режим
Electron по-прежнему может раскрывать реальное оборудование машины; строгий
режим блокирует часть API и этим отличается от обычного Chrome. Пассивный
TCP-отпечаток мобильного прокси формируется на стороне прокси и не исправляется
JavaScript-подменой в клиенте. Гарантии нераспознаваемости здесь нет.

Следующий этап проверяет нативным Electron-тестом, что основной документ,
dedicated worker и сторонний iframe согласованы по Windows User-Agent,
Client Hints (если API доступен движку), языкам, часовому поясу и числу ядер.
Проверка также сопоставляет `navigator.doNotTrack` с HTTP-заголовком `DNT`:
настройка профиля не должна выдавать противоположные значения в JS и сети.
Нативные GPU/Canvas/audio в обычном режиме этим изменением не изолируются.

## SharedWorker и ServiceWorker

Ранее нативный тест обнаружил системный Electron User-Agent в SharedWorker.
Подключение через отладчик отдельной страницы не решало проблему: shared
workers были недоступны, а ServiceWorker зависал до готовности его runtime.

Настольный клиент теперь запускает браузерный процесс через небольшой
координатор с наследуемыми анонимными каналами `--remote-debugging-pipe`.
Сетевой порт отладки не открывается; renderer не получает доступ к каналу.
Sandbox, contextIsolation, прежние хранилища профилей, single-instance lock
и штатное сохранение перед выходом остаются в браузерном процессе.

Browser-level auto-attach устанавливается до открытия persistent sessions.
SharedWorker и ServiceWorker приостанавливаются до первой строки кода и
получают политику своего BrowserContext: UA/UA-CH, язык, часовой пояс,
число ядер и скрипт ограничений профиля. Неизвестный контекст не запускается
без явно назначенной политики. Основная панель разрешена отдельно.

Важная граница текущего Chromium: неожиданно остановленный уже установленный
ServiceWorker не всегда приостанавливается заново до выполнения кода.
Поэтому потеря его runtime или приватного канала **блокирует сеть и останавливает
профиль**, а не продолжает работу с неподтверждённой защитой. Пользователь
получает уведомление. Требуется явно открыть профиль снова. Это не обещание
прозрачного восстановления после любого сбоя и не гарантия отсутствия любых
утечек. В обычном режиме регистрации ServiceWorker сохраняются при штатном
закрытии; строгий режим, как прежде, очищает регистрации перед запуском.

Нативные тесты проверяют параметры с первой строки скрипта, classic/module
workers, два профиля одновременно, HTTP-заголовки, зимнее и летнее смещение
Date, повторное открытие профиля и полный перезапуск приложения. Отдельно
проверяются остановка при потере защиты, отсутствие влияния на второй профиль
и сохранность cookies, localStorage и CacheStorage. Тесты используют только
синтетические данные и loopback-сервер; результаты не являются измерениями
реального пользовательского профиля на BrowserLeaks.

GPU/Canvas/audio/шрифты этим изменением не эмулируются. Обновление веб-панели
само по себе не защищает workers старого настольного клиента: нужен новый
бинарный клиент с этой реализацией.

Миграция `20260929100000_proxy_geo_timezone.sql` добавляет только необязательное
поле. До её применения список прокси и проверка соединения используют прежнюю
схему, поэтому панель остаётся работоспособной; определённый пояс при этом
ещё не сохраняется между загрузками.
