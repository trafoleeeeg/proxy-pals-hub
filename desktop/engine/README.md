# Нативный движок Umbra

## DNS-prefetch: исправление после аудита 0.4.32

`electron-dns-prefetch.patch` добавляет override `NetworkHintsHandlerImpl::PrefetchDNS`
в browser process: запросы спекулятивного DNS из renderer не передаются в
`ResolveHost`. Это покрывает link/HTTP Link hints, hover, meta on и вложенные
документы, включая srcdoc/about:blank/blob/data. Обычная загрузка сайта и
явный resolver API не отключаются; DOM и JavaScript API сайтов не подменяются.
Защита применяется ко всем сессиям этого движка, включая панель и direct mode;
компромисс — отсутствие оптимизации предварительного DNS-разрешения.

Проверка `IPv6 TURN` в desktop-тестах теперь требует отсутствия сетевых DNS-задач
для всех указанных контекстов в Windows. На прежнем screen5 тест воспроизводимо
падает; Linux CI с stock Electron выводит явное предупреждение о неподдерживаемой
нативной защите. Это не доказательство отсутствия других DNS/IPv6-утечек.
Стабильный клиент 0.4.32 сам по себе от изменения исходников не обновляется.
Новый архив `screen6` закреплён SHA-256 в `source-lock.json`. Его статус
`experimental-tested-do-not-release` намеренно блокирует автоматический стабильный
выпуск до отдельного решения о релизе приложения. Технический prerelease движка
не меняет `latest.yml` и не обновляет установленные клиенты.

На распакованном screen6 прошли 143/143 desktop-теста, два запуска screen/hardware
и font fixtures, а также rendering audit normal/strict-exception/font-isolated.
Во всех 8 ранее уязвимых сценариях DNS-prefetch сетевых resolver-событий нет;
обычные fetch/iframe и явный resolver-control продолжают работать.

## Эксперимент: отдельный набор шрифтов

В рабочей ветке добавлен `await session.setUmbraFontIsolation(files)`.
Клиент и редактор поддерживают opt-in, закреплённый ZIP `screen5` содержит API.
На старых движках переключатель недоступен, запуск изолированного профиля
отклоняется. Windows CI обязательно запускает font fixture именно на
скачанном архиве, затем проверяет файлы и лицензии в упакованном приложении.
Архитектура, ограничения и критерии проверки описаны в
[`docs/font-isolation.md`](../../docs/font-isolation.md).
Файлы тестового набора закреплены в `font-bundle-lock.json`; нативный тест
отказывается запускаться при несовпадении их SHA-256.
Ресурсы и лицензии включены в конфигурацию упаковки; тот же контроль целостности
выполняется при запуске изолированного профиля.

## Следующий этап: нативные CPU/RAM и HTTP memory hints

`session.setUmbraHardwareMetrics({ hardwareConcurrency, deviceMemory })`
задаёт неизменяемые сообщаемые значения до запуска renderer сессии. Допустимы
1–256 логических потоков и стандартные корзины памяти Chromium:
0.25, 0.5, 1, 2, 4, 8 ГБ. Повторная установка тех же значений разрешена;
изменение после первого renderer, включая worker без страницы, отклоняется.
Это политика BrowserContext: приложение передаёт её каждому renderer при
запуске, после обработки `additionalArguments`. Посторонние одноимённые
аргументы удаляются даже для сессии без политики.

Blink читает эти значения в общих нативных getters Navigator/WorkerNavigator.
При наличии API клиент убирает прежние JavaScript-getters и CDP-подмену числа
потоков. Отдельно сетевой guard заменяет уже присутствующие `Device-Memory`
и `Sec-CH-Device-Memory`; без согласованных сервером hints новые заголовки
не добавляются. Это необходимо потому, что browser-side Client Hints могут
вычисляться независимо от renderer. Интеграционный тест проверяет передачу
синтетических заголовков через настоящий session network stack; optional
Accept-CH на loopback HTTP Electron может не согласовать.

Запуск нативного fixture:

```powershell
node desktop/engine/run-screen-native.cjs D:\umbra-engine\src\out\UmbraTesting\electron.exe hardware
```

Fixture не использует preload или debugger emulation: два разных профиля,
первый inline script, OOPIF, dedicated/shared/service workers, popup, краш
renderer, закрытие/открытие окон и два полных запуска на одном loopback origin.
Проверяются нативность getters, запрет поздней смены политики и отсутствие
влияния на обычную сессию. Результаты не печатают реальные CPU/RAM компьютера.

Политика меняет сообщаемые API-значения, а не реальную производительность,
размер heap, планировщик, GPU/Canvas, аудио или установленные шрифты.

Локальная проверка `screen4`: оба нативных fixture проходят на двух запусках;
аппаратный fixture повторно прошёл на распакованном ZIP. Полный desktop-набор
на этом ZIP с обязательными native/DPAPI проверками — 131/131, без пропусков.
SHA-256 ZIP закреплён в `source-lock.json`. Первоначальный аппаратный тест
выявил обход через `additionalArguments`: `AppendArg` не попадает в таблицу
switches, поэтому одного `RemoveSwitch` недостаточно. Зарезервированные
аргументы теперь фильтруются до добавления, с проверкой разных префиксов и
регистра. На `screen3` новый fixture ожидаемо отклоняет отсутствующий API.

## Следующий этап: цветовые параметры экрана

В тестовом движке после 0.4.31 найдено воспроизводимое расхождение: у
синтетического 30-битного профиля `screen.colorDepth` уже показывал 30, а
CSS `(color: 10)` читал физический монитор и не совпадал. Для сессии с
политикой экрана Blink теперь согласует `color`, `monochrome`, `color-gamut`
и `dynamic-range`/`video-dynamic-range`: глубина компонента выводится из
профильного `colorDepth`, цветной экран считается sRGB SDR. Физические
цветовые возможности без политики не меняются. На прежнем движке новый тест
даёт `colorMedia=false`; после патча он проходит в первом inline script,
стороннем OOPIF и после двух запусков. Полный desktop-набор — 129/129.

Это только согласование наблюдаемых значений CSS. Оно не виртуализирует
вывод изображения, GPU, Canvas, WebGPU, аудио или шрифты и не гарантирует
нераспознаваемость. Новая сборка остаётся экспериментальной до Windows CI
и проверки на разных мониторах/DPI.

## Следующий этап: ориентация экрана

После 0.4.31 синтетический портретный профиль выявил расхождение:
`screen.width`/CSS показывали портретные размеры профиля, а
`screen.orientation.type` — ориентацию физического монитора. Патч Chromium
теперь выводит `screen.orientation.type` и `angle` из неизменяемой политики
экрана профиля; если доступен устаревший `window.orientation`, он возвращает
согласованный угол. Поворот физического экрана не должен создавать событие
изменения ориентации у профиля. Без политики поведение Chromium не меняется.

Регрессионный тест проверяет альбомные и портретный профили в первом inline
script, стороннем OOPIF, popup, после краша renderer и после двух запусков.
На локальной инкрементальной тестовой сборке он прошёл; полный desktop-набор
на этом же движке — 129/129. Это не подтверждает корректность на нескольких
мониторах и DPI и не устраняет раскрытие GPU, Canvas, аудио или шрифтов в
обычном режиме. Для CI опубликован отдельный prerelease ZIP
`umbra-engine-v44.4.5-screen2` с SHA-256 из `source-lock.json`; старый ZIP
0.4.31 не менялся. До публикации нового клиента нужны зелёный Windows CI и
отдельная проверка на разных мониторах/DPI.

29 сентября 2026 тестовый Electron собран из закреплённых исходников. Нативный
тест прошёл на двух запусках (включая CSS/JS стороннего OOPIF и zoom), а
интеграционный тест клиента и 128 тестов desktop прошли на этой сборке.
Тот же нативный тест прошёл на распакованном `dist.zip`; все 128 тестов
прошли на нём последовательно. В локальном параллельном прогоне один нативный
fixture сорвался при конкуренции за Windows-ресурсы; изолированный повтор
прошёл, поэтому Windows CI запускает нативный набор последовательно.
Пробный NSIS-установщик собран из официального `electron_dist_zip`, его
SHA-512, blockmap, содержимое `app.asar` и маркер нативного API проверены.
ZIP тестового движка имеет SHA-256 из `source-lock.json`. CI обязан скачать
только этот ZIP и проверить хеш: штатный Electron больше не может незаметно
попасть в установщик. Тег приложения пока блокируется состоянием
`experimental-tested-do-not-release`.

Это **тестовая** конфигурация GN с включёнными DCHECK, не проверенный
production build. До стабильного выпуска остаются решение о релизной
конфигурации, испытание готового приложения на разном DPI/мониторах и финальная
проверка безопасности. Автообновление пользователей не запускать.

## Состояние

Текущая конфигурация — **штатная non-component testing**, `is_component_build=false`.
Первую попытку component build остановил `lld-link` на DLL Abseil: её Chromium
export list требовал отсутствующие libc++ symbols. Electron патчит libc++ ABI
с версии 2 на 1; его штатный `testing.gn` также использует non-component build.
Переопределение возвращено к этому значению, resource allowlist снова наследуется
из Electron. Ни undefined symbols, ни проверки линковщика не подавлялись.
Новый GN-граф больше не содержит DLL Abseil, сборка запущена повторно без очистки.
Ниже сохранена история предыдущих стадий, включая отвергнутую component-попытку.

Написан и проверен прототип. Положительные нативные тесты и интеграция с
клиентом прошли на тестовой конфигурации; это НЕ подтверждает защиту всех
аппаратных API или готовность к стабильному выпуску. Ниже сохранена история
подготовки и промежуточных проверок.
Существующий `desktop/test/runtime-screen-coherence.test.cjs` не ослаблен.

цель win/x64. Продолжать `gclient sync --nohooks --no-history -j 4` только из
этого каталога. Для hooks/build потребуются `DEPOT_TOOLS_WIN_TOOLCHAIN=0`,
`vs2026_install=D:\umbra-engine\toolchain\BuildTools`, а также локальные
TEMP/TMP, CIPD/VPYTHON/UV caches в `D:\umbra-engine`. Сначала закончить sync,
затем проверить штатные патчи Electron, потом применять прототип Chromium.
В локальном `src/electron` изменения прототипа уже есть: повторно его патч
не применять, прежде проверить `git diff` и `git apply --reverse --check`.

Для воспроизводимого окружения можно dot-source `Enter-EngineEnvironment.ps1`
из отдельного PowerShell-процесса. Скрипт направляет временные файлы и кэши
на D: без изменения системного PATH, registry или глобальной Git-конфигурации.

## Прототип политики

- Main process вызывает `session.setUmbraScreenMetrics` **до** создания страниц.
- Шесть числовых полей: `width`, `height`, `availableWidth`, `availableHeight`,
  `colorDepth`, `deviceScaleFactor`. Некорректные значения отвергаются.
- Настройки хранятся на BrowserContext. После первого использования запрещено
  менять политику; повторная передача идентичных параметров разрешена.
- Настройки передаются через WebPreferences/Mojo в Blink Settings каждой view,
  включая OOPIF. Значения дополнительно проверяются на границе IPC.
- Прототип меняет web-visible Screen getters, CSS device dimensions и DPR.
  Физические VisualProperties, compositor и масштаб ввода не подменяются.
- CSS resolution и JS DPR должны учитывать page zoom одинаково, сохраняя
  заданный профильный DPR вместо host DPR. Это требует проверки на сборке.
- Без политики сохраняется стандартное поведение движка.

Это не утверждение о защите всех экранных/аппаратных API. В частности,
Window Management/ScreenDetails, экранные color media в выпущенном screen2,
OffscreenCanvas/worker media evaluation и события при смене монитора требуют
отдельной проверки; существующие запреты разрешений не заменяют такой аудит.
Прототип также НЕ эмулирует GPU, Canvas, аудио или шрифты.

## Порядок применения

1. Синхронизировать точные исходники и зависимости без запуска сборки.
2. Применить штатные патчи Electron его штатным механизмом.
3. Проверить и применить `chromium-screen.patch`, `chromium-hardware.patch`
   и экспериментальный `chromium-fonts.patch`
   относительно корня Chromium;
   `electron-screen.patch` и `electron-dns-prefetch.patch` — относительно каталога Electron.
   Патч Chromium подготовлен на выбранных исходных файлах тега; совместимость
   со всеми штатными патчами Electron должна быть проверена на полном дереве.
4. Собрать тестовый Electron x64 с sandbox и site isolation. Не отключать
   защиту ради прохождения теста. Не подменять установленное приложение.
5. Запустить из репозитория Umbra:

   ```powershell
   $env:TEMP = 'D:\umbra-engine\temp'
   $env:TMP = $env:TEMP
   node desktop/engine/run-screen-native.cjs D:\umbra-engine\src\out\UmbraTesting\electron.exe
   ```

Тест использует временные синтетические профили и loopback HTTP-сервер,
проверяет первые inline scripts и настоящие CSS rules без preload/CDP.
Проверяются две разные сессии, вложенные iframe с подтверждённым OOPIF,
resize, page zoom, навигации, наследование popup, принудительное пересоздание
синтетического renderer, независимость сессии без политики и два запуска браузера.
Эти сценарии пройдены на тестовом собственном движке. Стандартный Electron
должен завершиться ошибкой `native screen API missing`.

Для выпуска 0.4.31 владелец отдельно разрешил использовать текущую проверенную
Windows-сборку движка. Она прошла синтетические native-тесты, повторный запуск,
полный desktop CI и проверку Windows-установщика/манифеста обновления. Это не
означает полной защиты: перемещение между мониторами с разным DPI, перечисление
экранов и поведение установленного клиента на разных реальных конфигурациях не
проверены. Сборка не является официальной release-конфигурацией Chromium.
Linux продолжает использовать штатный Electron без нативной политики экрана.
GPU, Canvas, audio и шрифты в обычном режиме отражают реальное оборудование.
